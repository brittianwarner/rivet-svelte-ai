# Deploying the starter

Deploy the web app and API/actor runner as separate Node services, and connect the runner to your Rivet deployment. The repository includes Railway infrastructure as code, container builds, and a deployed-stack acceptance command.

## Railway: self-hosted Rivet 3.0

The new [Railway infrastructure-as-code workflow](https://docs.railway.com/infrastructure-as-code) lives in [`.railway/railway.ts`](../.railway/railway.ts). It provisions:

| Resource      | Responsibility                                                   |
| ------------- | ---------------------------------------------------------------- |
| `web`         | SvelteKit Node server; public HTTPS; proxies `/api/*` privately  |
| `api`         | Hono + Rivet actor node; private networking only                 |
| `rivet`       | Rivet Engine 3.0.1, pinned by image digest; public actor gateway |
| `rivet-log`   | Persistent engine log volume; one replica, one attached disk     |
| Object bucket | Durable object storage, connected by Railway variable references |

The admin credential is generated by Railway. It is referenced by the API, never copied into the web service or committed. Browsers receive renewable 15-minute tokens limited to actor creation/reads and gateway traffic. Node, pool, token administration, actor deletion, and KV access are not granted. These are **anonymous demo credentials for the namespace**, not private user/session authorization. Keep provider keys absent for the public starter.

### First deployment

Use Node 26, Bun 1.4.4, and a current Railway CLI with `railway config` support. Install dependencies with `bun install --frozen-lockfile`, then sign in with `railway login`.

1. Fork the repository and change `repository` in `.railway/railway.ts` to your fork. Keep the workspace root as the build context. Railway builds all three services directly from `main`; GitHub CI provides validation but does not gate deployment. For a new project, initially set `webDomain` to `undefined` and `domains` to `[]`; custom domains must be attached once before IaC can manage them. Merge your deployment configuration into `main` before provisioning.
2. Create an empty Railway project in your intended workspace. The checked-in bucket name preserves the original project's bucket; a new project can use it as-is or rename it **before the first apply**. Existing projects must first import and preserve their other resources with `railway config pull`.
3. Link and review the infrastructure plan:

   ```sh
   railway link --project YOUR_PROJECT_ID --environment production
   railway status --json
   bun run railway:plan
   railway config plan --out /tmp/rivet-railway-plan.json
   railway config apply --plan /tmp/rivet-railway-plan.json
   ```

4. Generate a public gateway domain once:

   ```sh
   railway domain --service rivet --port 6420
   ```

   For a generated web domain, run `railway domain --service web --port 3000`. For a custom domain, connect it to `web` on port 3000 in Railway first, then set `webDomain` and restore the `domains` declaration in IaC. Verify DNS and certificate status with `railway domain status YOUR_DOMAIN --service web`, then plan and apply the origin changes. The original production deployment uses `https://svelteactors.dev`.

   Railway's generated domains are not authored in IaC. Variable references connect them automatically. Initial application deployments can fail until the domains exist; after creating them, deploy the application sources again:

   ```sh
   railway redeploy --service api --from-source --yes
   railway redeploy --service web --from-source --yes
   ```

5. Wait for all three services to become healthy, then verify the actual actor path:

   ```sh
   bun run test:deployment https://YOUR_WEB_DOMAIN
   ```

   This creates one uniquely named acceptance counter, verifies a WebSocket event and HTTP action, and checks that its browser token cannot list nodes. It never calls an AI provider. Save the printed actor key/count to verify recovery after a restart:

   ```sh
   SMOKE_ACTOR_KEY=acceptance-... SMOKE_EXPECT_COUNT=3 \
     bun run test:deployment https://YOUR_WEB_DOMAIN
   ```

The API startup script waits for storage and creates the named `starter` namespace and its default node pool only if missing. Namespace selection is passed explicitly to browser clients. Each Railway environment has its own control plane, volume, and bucket instance; references remain inside that environment. Each API image records a build-time release version that remains stable across restarts. Set `RIVET_NODE_VERSION` explicitly when promoting an older image: rollbacks also need a version newer than the active release. Do not reuse an old version for a changed release.

### Operate with a coding agent

Start every infrastructure task with `railway status --json` and a read-only `bun run railway:plan`. Confirm the intended project/environment in both outputs. Change `.railway/railway.ts`, review the diff, and apply a pinned plan. Application changes deploy from the configured GitHub branch; CI runs independently, while Railway health checks gate deployment; do not upload an arbitrary local checkout with `railway up`.

Use `railway logs --service api --lines 100`, `railway logs --service rivet --lines 100`, and `railway deployment list --service web` to diagnose a release. Logs may contain application data: inspect narrowly and never paste credentials. Keep secret variable values in Railway; use references or `preserve()` when importing them.

Custom web domains require changing both `WEB_ORIGIN` (web build) and `WEB_ORIGINS` (API). Custom gateway domains require `RIVET_PUBLIC_ENDPOINT`. Rebuild web after changing its origin. Keep API/peer/metrics ports private. Do not expose the peer port 6421 or metrics port 6430 publicly.

### Storage and availability

This is a single-instance starter. Engine maintenance interrupts actor traffic. The bucket and volume persist data but do not provide multi-node availability. The [Rivet self-host guide](https://rivet.dev/docs/deploy/self-host/control-plane/docker-compose/) recommends three or more control-plane instances for production availability.

Rivet requires at least 4 GiB and 10% free disk to admit storage. The starter's 5,000 MB log volume has limited headroom: monitor free space and expand it before onboarding significant traffic. Do not lower Rivet's safety thresholds to force startup. Configure Railway volume backups and an object-storage backup/restore policy appropriate for your data, and test recovery before relying on it. Deleting the volume or bucket is not an application rollback.

## Build and run

```bash
bun install --frozen-lockfile
bun run validate

# API service (from repository root)
bun run --filter @example/api start

# Web service (a separate process, from repository root)
bun run --filter @example/web start
```

The API runs native TypeScript on Node 26; SvelteKit builds to `apps/web/build`. Install from the workspace root and keep the workspace packages available. The API does not require an application bundling step.

For a container, set `API_HOST=0.0.0.0` and the API port from your host. For the web service, set `HOST=0.0.0.0` and its `PORT`. Configure `paths: { origin: "https://app.example.com" }` inside `sveltekit(...)` in `apps/web/vite.config.ts` before building. SvelteKit 3 replaces adapter-node's old `ORIGIN` environment variable with this configuration. Set `API_ORIGIN` to the API's private HTTP URL. The production web server does not read root `.env` automatically.

## Connect a remote engine

Configure these only on the API service:

- `RIVET_ENDPOINT`: your engine endpoint.
- `RIVET_TOKEN` and `RIVET_NAMESPACE`: credentials and namespace supplied by Rivet.
- `RIVET_NODE_VERSION`: a monotonically increasing integer release number; follow your provider's version/upgrade configuration.
- `RIVET_PUBLIC_ENDPOINT`: the browser-safe public endpoint supplied by Rivet. Include only public client access material if required by your deployment, never the management secret.
- `WEB_ORIGINS`: comma-separated exact public web origins, such as `https://app.example.com`.
- Optional model credentials and model IDs.

With `RIVET_ENDPOINT` set, the registry does not start a local engine. Follow the current [Rivet deployment documentation](https://rivet.dev/docs/) for the selected host and configure its runner pool. Use HTTPS/WSS on public endpoints. Do not rely on ephemeral container disks for local-engine production persistence.

This template uses long-running Rivet 3.0 nodes and the documented scoped-token API. Check the documentation for your exact engine version before enabling additional runtime modes.

## Turn the demo into an application

The template intentionally does not choose an identity provider. Before public use with private data or model spending:

1. Authenticate users through your application and verify that identity on the actor connection.
2. Authorize the requested actor key against the verified user/organization. Opaque keys alone are not authorization.
3. Protect the HTTP counter route as well as direct actor actions. CORS is not an authentication layer.
4. Replace the public `ACTOR_TOKEN` demo parameter. It is returned by `/client-config` and cannot protect data from a visitor.
5. Add per-user/organization rate limits, actor-creation limits, AI budgets, retention, and actor cleanup. One active request per conversation is not an account-wide spending limit.
6. Add structured telemetry and redact provider credentials and sensitive prompts.

## Verify a release

`/health` proves the API process is listening. `/health/actors` checks the Rivet node runtime and is the Railway deployment gate; `/ready` only reports provider selection. None replaces a real actor action, event, or persistence test.

Verify a typed actor action and event, a second browser, reconnect, restart persistence, denied unauthorized access, and an actual model turn in the deployed environment. For crash-resumable AI work, add workflow recovery tests. Test expected concurrency separately. Deploy reviewed changes through your normal release pipeline; the Railway configuration and container sources are versioned in this starter.

## Local restart acceptance

`bun run test:restart` creates a temporary standalone engine and checks that the counter and completed chat transcript survive stopping and restarting the API/actor runner. The engine stays running during this acceptance test. Test storage is isolated from the developer's engine and removed afterward.

Full local engine recovery remains unqualified on RivetKit/Engine 3.0.1: an isolated test that also restarted the engine observed `depot/routing_unavailable`, `depot/command_capacity`, and actor readiness timeouts on subsequent reads. This does not establish data loss or successful recovery. To reproduce that investigation separately, run `FULL_ENGINE_RESTART=1 bun run test:restart`. Qualify engine restart recovery on the engine version and deployment you intend to operate before depending on it.

See the [local engine recovery report](local-engine-recovery.md) for reproduction steps, settings, and observed errors.

## Rivet 3.0 configuration references

- [Self-host configuration](https://rivet.dev/docs/deploy/self-host/control-plane/configuration/) and [storage](https://rivet.dev/docs/deploy/self-host/control-plane/storage/): official Engine image, `RIVET__STORAGE__*` settings, one persistent log volume, and S3 object storage. No patched Engine or SDK is used.
- [Namespaces](https://rivet.dev/docs/namespaces/) and [scoped tokens](https://rivet.dev/docs/jwt/): named namespace, backend-only admin token, explicit browser grants, and renewable credentials.
- [Node health](https://rivet.dev/docs/deploy/self-host/nodes/health-checks/) and [versions](https://rivet.dev/docs/versions/): native registry health and increasing release versions.
- [Railway bucket URL style](https://docs.railway.com/storage-buckets) and [Rust object_store endpoint behavior](https://docs.rs/object_store/latest/object_store/aws/struct.AmazonS3Builder.html#method.with_virtual_hosted_style_request): the small startup script formats the bucket hostname and uses the supported `AWS_VIRTUAL_HOSTED_STYLE_REQUEST` setting. It does not alter Rivet storage behavior.
- [Production checklist](https://rivet.dev/docs/deploy/self-host/control-plane/production-checklist/): a production HA cluster calls for three or more instances, versioned object storage, separate disks of at least 100 GiB, monitoring, and a tested restore. This smaller Railway starter deliberately does not claim that deployment profile.
