# Railway infrastructure

`.railway/railway.ts` is the infrastructure source of truth. It uses the official `railway/iac` SDK; there are no legacy `railway.json` or `railway.toml` files.

See [the deployment guide](../docs/deployment.md) for first deployment, generated domains, acceptance, and operations.

```sh
railway status --json                 # Confirm project AND environment first
bun run railway:plan                 # Read-only diff, values redacted
railway config plan --out /tmp/railway-plan.json
railway config apply --plan /tmp/railway-plan.json
```

Keep plan artifacts out of Git. Apply the exact reviewed plan. Inspect `--json` apply status and verify resulting service instances; a successful CLI exit alone does not prove the environment applied. Never add `--confirm-destructive` to routine automation. A volume deletion, shrink, detach, or placement change requires a separate data-preservation plan and explicit authorization.

`railway config pull` imports an existing project with secrets preserved. Do not use `--include-variables`, `--decrypt-variables`, or `--show-values` in agent logs. Do not use `ctx.randomString()` for secrets: it is deterministic. The control-plane credential is generated by Railway and referenced only by the API.

Generated Railway domains are managed through `railway domain`; Railway excludes them from the authored IaC file. Custom domains belong in the file after their one-time attachment to a service; the CLI currently rejects first-time custom-domain registration through IaC. Never give the API a public domain: the web service reaches it over Railway's private network.

Keep one control-plane replica attached to its volume. This starter is a single-instance deployment, not a high-availability cluster. Never attach two engines to the same log volume or object prefix.
